# 案例 2：falsify——自建四层对抗审计体系

## TL;DR

受量化交易审计纪律启发，为「数据报告 / 代码 / 部署产物 / 软件行为」四类对象自建了一套对抗审计体系，核心立场是**复核时默认它是错的**。多次拦截六位数金额级的口径错误和脏数据上线，并把「复核」从依赖个人变成依赖机器闸门。

## 背景与问题

电商周报/看板是决策依据，但数据从平台后台到最终产物要经过抓取、解析、聚合、生成四层，每一层都可能引入错误。传统「自查」无效——作者立场天然倾向于相信自己的产物。需要一个制度性的对抗者。

## 体系设计（四层）

```
report-falsify   → 审数据报告（口径/闭合/脏值/假绿/越权结论）
falsify-generic  → 审部署产物（web-deploy / data-artifact / code-basic / code-structure）
falsify（引擎）   → 审代码（5 类 claim，权威镜像 + 漂移探针）
product-falsify  → 审软件行为（宣称 vs 实际，发版前实弹走查）→ 见案例 4
```

核心纪律三条：

1. **生产与复核不同立场**：生成者默认对，复核者默认错，且必须自拟 kill-shot（禁止形式审计）
2. **Cutline 三分类**：Must Fix（不修就会导致错误决策，清空前不许发）/ Known Debt（真实风险但暂不阻塞，必须带升级触发器）/ Delete（无具体失败模式）
3. **机器闸门**：可机器判定的检查固化成脚本，agent 无法删改；判据改动必须重跑行为契约夹具，exit 1 = 漂移

## 实战战果（挑三个最能讲的）

### A. 口径混淆 Must Fix（差 13.5%）

首战周报：子渠道 GMV 加总与直播间画面 GMV 差 13.5%。根因是「成交口径 vs 支付口径」跨表混用——不是数据丢失，是**两个都对的数字被放在了同一个等式里**。修复后 PASS_WITH_DEBT 才放行。

### B. 脏 ROI 上线事故（假 10.79 vs 真 7.58）

某店素材 ROI 因列错位显示 10.79，构建脚本声称已修正为 7.58 但**产物从未重建**——「文档说修了」和「产物真的变了」是两件事。此后新增检查：文档声称「已修正/已部署」必须有产物 mtime/值支撑，否则判假绿 Must Fix。两店素材 ROI 差距从误报的 1.64× 修正为 1.16×，直接改变了「素材质量是根因」的经营判断。

### C. 大场复盘归因反转（两次同构错误）

某大场复盘初版 P0 结论「流量断崖疑似投放停止」。对抗审对时分时数据后推翻：投放在跑，断的是直播间自然进人；且放量时段消耗与上午持平——**放量是免单撬动的自然流量，不是付费堆的**。后续又被口径纠正反转一次「免单拉人不拉钱」（浅层人群窗口看成交节奏不看 GPM：免单窗 1.63-1.73 单/min，高于基线 27-35%）。两次错误同构：**用了错误的分母/口径做归因**。该复盘经历 12 轮迭代、三轮独立 agent 复核（两轮 BLOCK 共 8 个 Must Fix 全修，含一次「批量编辑静默失败报已修」的假绿抓现行）。

## 防假绿的元设计（面试官最爱问的部分）

- **审计器自审**：一条无法被证明会翻红的护栏不是护栏，只是注释——每个审计器带故障注入 selftest，自审不过整轮审计作废
- **行为契约回放**：判据改动必须重跑夹具组，防止「检查悄悄失效」
- **失败零打点 = Must Fix**：失败路径与成功路径同权
- **Debt 透传**：exit 0 不再被翻译成「没有债务」——PASS_WITH_DEBT 是独立 verdict

## 可迁移能力

- 把「数据可信」从口号变成 exit code——这套东西在任何数据团队都缺
- LLM 时代尤其值钱：AI 生成内容必须过对抗复核，我有四个版本的实战迭代
- 「口径」敏感度：知道每个数字在哪里、被谁、以何种定义生产出来
