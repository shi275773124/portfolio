# 案例 1：周报全自动化管道（抓取 → 校验 → 生成 → 复核 → 上线）

## TL;DR

把一份原本 20-30 分钟人工操作的电商周报，做成全链路自动化管道，压缩到 5-8 分钟；期间解决了一系列只有生产环境才会暴露的工程问题（平台节流、口径钳位、列错位、跨表闭合），并配了机器校验闸门保证产物正确性。

## 背景与问题

抖音电商经营周报需要从平台多个后台（罗盘/千川）取数：交易明细、直播间数据、行业大盘、搜索表现、广告素材、退款……每周人工翻操作手册、逐个跑脚本、手工算渠道 ROI，单份 20-30 分钟，且极易出错（后续对抗复核证明这不是杞人忧天——见案例 2）。

## 我做了什么

### 1. 数据采集层（最难的部分）

- **CDP + Playwright 逆向平台后台**：调试口接管浏览器，截获内部 XHR 接口，逐场抓取直播间流量来源
- **「download-first」切源**：发现页面文本接口会被平台「滚动窗」钳位——周口径数据被静默替换成滚动 7 天（实测偏差 11%）。改为优先消费官方导出 xlsx，并对导出件做**窗口自证**（文件名窗口/日期列/元数据四项校验），fail-close 回退并如实披露
- **签名 URL 重放**：导出中心「下载明细」实际生成签名 URL——点一次铸 URL、改日期参数、页面内 fetch 重放，五个数据板块全部打通
- **表头驱动解析**：同一张报表在不同店铺后台列布局不同（一家 14 列一家 16 列），固定列序解析产出 CTR=1041%、CVR=19 万的脏值。重写为表头别名匹配 + 自洽性校验（结算率+退款率=100、CPM×消耗≈花费）
- **对抗平台节流的工程细节**：JS 合成点击不被平台识别（必须真实点击模拟）、后台 tab 渲染暂停（需前台激活）、浏览器自愈守护进程 + 15 分钟看门狗、资源锁防多任务互杀

### 2. 管道与闸门层

- 一条命令收口：自然周抓取 → 口径闸门 → 报告生成 → 19 张在线表格 → 门户上线，未结算自动重试
- **产物↔源对账闸门**：报告数字必须能对回源文件，对不上拦发布
- **人机分离 overlay**：机器产物与人工结论分层，重生成不冲人工内容
- 幂等设计：抓取元数据 sidecar 记录窗口自证，达成窗口≠请求窗口必须重抓

### 3. 生成层

- 数据驱动的表格生成（typed 数值化：百分比/金额/占位各自正确渲染，字符串数字永不渲染）
- 每周自动追加新板块（大场预热：商品曝光/点击/加购 + 人工预约合并）

## 验证

| 指标 | 值 |
|---|---|
| 单份周报人时 | 20-30min → 5-8min |
| 滚动窗钳位实测偏差 | 11%（同一指标两种窗口口径） |
| 退款口径独立链路 | 发货前 17.35% / 发货后 28.31%（对比「未退完瞬时值 23.59%」的误读） |
| 列错位脏值 | CTR 1041% / CVR 190,869 / ROI 错挂（10.79 vs 真实 7.58） |

## 可迁移能力

- 无人监督下把脆弱的爬虫做成生产级（幂等/重试/自愈/exit 码分级/fail-close）
- 「口径」敏感度——大多数团队栽在「数字看起来合理但口径是错的」
- 平台对抗工程（签名 URL、节流、渲染节流、风控拦截）的完整踩坑经验
