# 案例 4：LLM 客户端与 product-falsify（故障注入组合测试）

## TL;DR

独立迭代一个 LLM 集成的桌面客户端（Rust Tauri + 前端，直播复盘工具），并为它自建「软件对抗审」体系 product-falsify：错误契约表、标准故障字典、NIST 2-way 组合矩阵、金样本回归。**首战实弹 32/32 全绿的同时当场抓出一个真 bug：402 额度耗尽被当瞬时错误重试满 3 轮（=12 次 LLM 调用浪费），失败提示还在诱导用户「再试一次」。**

## 产品背景

直播复盘工具（桌面客户端）：从平台后台自动抓取直播间分钟级数据 + 逐字稿，LLM 生成复盘报告，内置知识库注入系统提示词，用户可自带 API key（含免费档）。迭代节奏：每周 1-2 个版本，52 项机械闸门（编译/单测/结构检查）全绿是发版底线。

## 问题：机械闸全绿，真实用户当天卡死

某版审计 PASS_WITH_DEBT 零 Must Fix，但**外部用户（免费档、新人、可能未登录）当天**就卡死在核心功能第二步。复盘出四个盲区：

1. **失败注不进**——真 API 只能测成功路径，LLM 失败序列没有仪器注入
2. **外部新人不在人设矩阵**——审计全在作者机（自带 key+已登录+缓存热），恰恰最不代表外部用户
3. **守卫文案指向不存在之物**（0 候选时提示「先采纳」）
4. **失败态→恢复的 UI 残留无人验**

## 我做了什么

### 1. product-falsify 体系（v0.1 → v0.8.0，实战驱动 8 个版本）

核心立场：**每个按钮文案/提示/徽标都是「宣称」，默认它错**，逐条自拟 kill-shot 实弹验证。每功能 8-14 问：空输入/断网/弹窗内报错/失败清场/重复点击/重启状态/历史回放/旁路并发/归因复测/失败落痕……

### 2. v0.8.0 审计能力工业化（调研微软/AWS/NIST 后落地）

| 业界实践 | 来源 | 我的落地 |
|---|---|---|
| 故障注入进 CI 门禁 | 微软工程手册、Azure Chaos | 发版闸门第 6 段 sweep --quick 常态化 |
| 故障类型学（预定义模板） | AWS FIS | 8 类原语：timeout/hang/reset/402/401/badjson/refuse/partial |
| 错误契约两侧一致 | contract testing | 12 语义类契约表 + 审计器三护栏 |
| 2-way 组合覆盖 50-97% 缺陷 | NIST 组合测试 | 人设×环境×故障 2×2×8=32 例配平跑批 |
| 金样本=真实事故+确定性重放 | LLM 应用测试实践 | 金样本库收编进 git，换机不缺件 |

**五 oracle 判定**：G0 开动 / G1 不炸 / G2 有出口 / G3 文案不撒谎 / G4 守卫可执行 / G5 恢复无残留。

### 3. 仪器：剧本注入桩 rig

自建 rig：真实前端渲染管线 + importmap 桩（桌面 API 全 mock）+ 单 handler 分发 + LLM 剧本队列（失败序列可编排）+ 人设编排。**仪器自己也要过冒烟，冒烟不过不得开工**——首战就抓出修复代码自身的 stale 失败卡 bug，当场自证价值。

### 4. 首战战果（32/32 GREEN 并抓真 bug）

- **402 QUOTA bug**：额度耗尽属 FAST_STOP 语义（重试毫无意义），但被归为瞬时错误重试满 3 轮（12 次 LLM 调用浪费），失败卡还画着重试按钮。修复：重试环断路 + QUOTA 分支指升级路径 + 弹窗分通道
- **文案击穿断路器的机制**：某版事故——后端错误经中文文案改写后，前端正则 `/timeout|没返回/` 不再命中「模型接口超时了」→ 断路失效照旧重试。契约表三护栏（完备/断路双族齐备/禁词）让这类 bug 从此是机器闸拦的死项
- 审计器自身也被自审修了 3 处（误报窗口粗扫/静默漏扫/selftest 注入目标错文件）

## 可迁移能力

- LLM 应用的可靠性工程：failure mode 分类学、错误契约、金样本回归——正是当下 AI 产品团队最缺的
- 「机械闸绿 ≠ 行为对」的测试哲学；失败路径与成功路径同权
- 桌面客户端独立交付全栈经验（Rust/前端/LLM 集成/发布流程/升级机制）
